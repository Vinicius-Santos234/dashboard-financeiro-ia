## 1. Objetivo

Aplicação web onde o usuário faz login, envia o extrato exportado do próprio banco
(OFX ou CSV), e vê os gastos categorizados por IA em gráficos interativos, com insights
em texto sobre o mês.

**Uma frase de sucesso:** um estranho abre o link, entra na conta demo, e em menos de
30 segundos entende no que aquele dinheiro foi gasto — sem eu explicar nada.

### 3.1 D2 revisada em 05/09 — de Supabase para Firebase

A decisão original era Supabase. Mudou por um motivo que não é técnico e não deve ser
maquiado como se fosse: **o plano gratuito do Supabase permite 2 projetos por usuário
somando todas as orgs**, os dois slots já estão ocupados, e um deles é um trabalho de
faculdade usado todo semestre — não dá para apagar. O bloqueio é permanente, não uma
espera.

Somam-se três razões a favor do Firebase neste projeto: já é conhecido, é gratuito no
plano Spark para tudo que a v1 precisa, e o outro projeto do portfólio
(`sistema-rdo-digital`) já usa Supabase — então aqui o Firebase mostra **um segundo
banco** em vez de repetir o primeiro.

**O que a troca custou, dito sem eufemismo:**

| Perda | Compensação |
|---|---|
| `unique (user_id, fingerprint)` | O fingerprint vira o **id do documento**. Um `create` num id existente falha sozinho — a garantia deixa de ser uma constraint declarada e passa a ser a estrutura do caminho |
| `group by category` em uma linha de SQL | Documento de **rollup mensal** (§4.5). O dashboard passa de um `group by` para **uma única leitura de documento** — na prática fica mais rápido, ao custo de manter o rollup em dia |
| `check` de enum, faixa e coerência | Validação nas Security Rules (§4.4), que são versionadas e testáveis |
| `ilike` para casar `rules` no banco | As regras do usuário são poucas; casam em memória no servidor |
| RLS valendo para **todo** acesso | Ver o parágrafo abaixo — é a perda real, e é onde o desenho precisou mudar |

**A perda que exigiu mudança de desenho.** No Postgres, a RLS vale inclusive para o
código do servidor: não há como o backend ler a linha de outro usuário sem desligar a
policy. No Firebase, o **Admin SDK ignora as Security Rules** — o servidor tem acesso
total, e as regras protegem apenas o caminho do cliente. Isso reintroduz exatamente o
risco que a §4.4 original rejeitava: um filtro esquecido numa tela nova.

A resposta é estrutural, não disciplinar: **os dados do usuário vivem em subcoleções sob
`users/{uid}/`**, e todo acesso do servidor passa por `lib/firestore/repo.ts`, cujas
funções recebem o `uid` como primeiro argumento e montam o caminho a partir dele. Não
existe query "de todas as transações" para alguém esquecer de filtrar — sem `uid` não há
caminho, e sem caminho não há query. É uma garantia mais fraca que a RLS e mais forte que
um `where` que se pode omitir. Fica registrado no README como está, sem arredondar.

## 4. Modelo de dados

### 4.1 A árvore

Tudo que pertence ao usuário mora **sob o `uid` dele**. Não é organização estética: é o
que garante que não exista query global para alguém esquecer de filtrar (§3.1).

```
users/{uid}                            perfil: email, criadoEm
users/{uid}/accounts/{accountId}
users/{uid}/imports/{importId}
users/{uid}/transactions/{fingerprint}   ← id = fingerprint (§4.3)
users/{uid}/rules/{padrao}               ← id = padrão normalizado
users/{uid}/insights/{YYYY-MM}
users/{uid}/rollups/{YYYY-MM}            ← agregado do mês (§4.5)
```

### 4.2 Documentos

```ts
type Account = {
  name: string
  institution: string | null
  kind: 'checking' | 'savings' | 'credit_card'
  createdAt: Timestamp
}

type Import = {
  accountId: string
  source: 'ofx' | 'csv'
  filename: string
  fileHash: string          // sha256; só para avisar "já importou este arquivo"
  periodStart: string | null   // 'YYYY-MM-DD'
  periodEnd: string | null
  rowsTotal: number
  rowsImported: number
  rowsDuplicated: number
  rowsDiscarded: number
  status: 'parsed' | 'categorized' | 'failed'
  error: string | null
  createdAt: Timestamp
}

type Transaction = {
  accountId: string
  importId: string | null
  occurredOn: string          // 'YYYY-MM-DD', ordenável como string
  month: string               // 'YYYY-MM' — sem group by, o filtro do mês é um campo
  amountCents: number         // inteiro. Negativo = saída
  descriptionRaw: string      // como veio do banco; nunca sai do servidor
  descriptionClean: string    // anonimizada (§7.1); é esta que vai à LLM
  fitid: string | null
  category: Categoria | null
  categorySource: 'ai' | 'rule' | 'user' | null
  confidence: number | null
  source: 'ofx' | 'csv' | 'bot' | 'openfinance'
  aiOptOut: boolean           // nunca enviar à LLM (§7.2)
  createdAt: Timestamp
}

type Rule = {
  pattern: string             // igual ao id do documento
  category: Categoria
  hits: number
  createdAt: Timestamp
}

type Insight = {
  body: { headline: string; items: InsightItem[] }
  model: string
  generatedAt: Timestamp
}
```

**`month` é campo, não derivação.** O Firestore não tem `group by` nem função de data em
query. Sem `month` gravado, filtrar o mês exigiria um range em `occurredOn` — que
funciona, mas obriga um índice composto a mais em toda consulta por categoria. Um campo
de 7 caracteres resolve, e é escrito uma vez no import.

**`amountCents` continua inteiro.** O Firestore não tem `bigint` — números são IEEE 754
de 64 bits, exatos até 2^53. Em centavos isso é R$ 90 trilhões, folgado. O que **não**
pode acontecer é alguém gravar reais fracionários aqui; as Security Rules recusam
(§4.4).

### 4.3 O fingerprint agora é o id do documento

A regra de formação continua a da versão Postgres, com uma diferença imposta pela
plataforma: **id de documento não pode conter `/`**, e FITID de banco às vezes contém.
Então o fingerprint passa a ser sempre hash hexadecimal, com prefixo dizendo de onde
veio:

```
com FITID confiável:  'ofx_' + sha256(accountId + '|' + fitid)
qualquer outro caso:  'h_'   + sha256(accountId|occurredOn|amountCents|descNorm|seq)
```

`seq` continua existindo pelo mesmo motivo de sempre: **dois cafés de R$ 8,00 no mesmo
lugar no mesmo dia são duas transações legítimas e idênticas.**

E o ganho da troca aparece aqui: gravar com `create()` num id que já existe **falha
sozinho**, sem constraint declarada em lugar nenhum. A deduplicação deixa de ser uma
regra que o banco aplica e passa a ser a forma da árvore.

### 4.4 Security Rules — o mecanismo, e o que ele não cobre

`firestore.rules`, versionado no repositório:

```
match /users/{uid} {
  allow read, write: if request.auth != null && request.auth.uid == uid;

  match /transactions/{fingerprint} {
    allow read:   if dono(uid);
    allow create: if dono(uid) && transacaoValida(request.resource.data);
    allow update: if dono(uid) && soMudouCategoria();
    allow delete: if dono(uid);
  }
}
```

Validam o que os `check` do Postgres validavam: `amountCents` inteiro, `category` dentro
do enum, `occurredOn` no formato ISO, `month` coerente com `occurredOn`, e campos
imutáveis (`fingerprint`, `accountId`, `amountCents`) que um update não pode tocar.

**O limite, dito às claras:** as regras valem para o SDK cliente. O **Admin SDK do
servidor as ignora**. O que protege o caminho do servidor é a árvore de §4.1 mais o
`repo.ts` de §3.1 — não as regras. O README diz isso com estas palavras; afirmar que "as
Security Rules protegem o sistema" seria a mesma promessa vazia que a §7.2 recusa a dar
sobre anonimização.

### 4.5 Rollup mensal — o que substitui o `group by`

```ts
type Rollup = {
  month: string                              // 'YYYY-MM'
  totalInCents: number
  totalOutCents: number
  count: number
  byCategory: Record<Categoria, number>      // centavos, sempre as 10 chaves
  updatedAt: Timestamp
}
```

Atualizado dentro de uma **transação do Firestore** sempre que transações entram ou uma
categoria muda. O dashboard lê **um documento** para desenhar a pizza inteira — contra um
`group by` que varreria o mês.

O risco desse desenho é conhecido e tem nome: **o rollup sai de sincronia com a
realidade.** Duas defesas, as duas obrigatórias:

1. `recalcularRollup(uid, month)` recomputa varrendo as transações do mês. É o botão de
   conserto e é barato (um mês são ~100 documentos).
2. Um teste que importa um lote, muda categorias, e afirma que o rollup **bate exatamente**
   com o recálculo. Sem esse teste, o rollup é um número bonito em que ninguém pode
   confiar.

### 5.1 O contrato que o Open Finance vai reusar

```ts
// lib/sources/types.ts
export interface RawTransaction {
  occurredOn: string        // ISO 'YYYY-MM-DD'
  amountCents: number       // negativo = saída
  description: string       // como veio, sem tratamento
  fitid?: string
}

export interface ParseResult {
  transactions: RawTransaction[]
  account?: ContaDetectada          // ACCTID, instituição, tipo, moeda
  periodStart?: string
  periodEnd?: string
  descartadas: LinhaDescartada[]    // linha, conteúdo, motivo
}

export interface SourceAdapter<Opcoes = void> {
  readonly id: 'ofx' | 'csv' | 'bot' | 'openfinance'
  parse(input: ArrayBuffer | string, opcoes: Opcoes): Promise<ParseResult>
}
```

Este é o ponto inteiro da inversão de ordem: quando o Open Finance entrar, ele implementa
`SourceAdapter` e **nada mais no app muda**.

> **Revisão em 05/09, ao implementar (E2):** o contrato original devolvia
> `RawTransaction[]` puro. Duas coisas obrigaram a mudar, e as duas apareceram só ao
> escrever o parser:
>
> - **`periodStart`/`periodEnd`/`account`** — a tabela `imports` tem essas colunas e o
>   dado só existe dentro do arquivo. Sem devolvê-los, o Route Handler teria que reparsear.
> - **`descartadas`** — a linha que o parser não consegue ler não pode sumir calada. É a
>   mesma doença do `parseAmountToCents` chutando um valor: o total do dashboard diverge
>   do extrato e não há pista de onde. Cada descarte carrega número da linha e motivo.
>
> O parâmetro `Opcoes` existe porque o CSV precisa do mapeamento de colunas e o OFX não
> precisa de nada.

### 5.2 O pipeline, na ordem em que o dado atravessa

```
arquivo → parse → normalizar → fingerprint → dedupe → persistir (sem categoria)
                                                            ↓
                              regras do usuário casam? ──sim──→ grava categoria (0 tokens)
                                                            ↓ não
                                          anonimizar → Gemini (lote 50) → validar → gravar
```

O arquivo **nunca é gravado em disco nem em bucket**. É parseado em memória e descartado
ao fim do request. Só as linhas persistem.

## 6. A camada de IA

### 6.1 O que sai da máquina

Só isto, e nada mais:

```json
[
  { "id": "t_01", "desc": "IFD*IFOOD SAO PAULO", "v": -4790, "d": "2026-08-14" },
  { "id": "t_02", "desc": "PIX ENVIADO",         "v": -5000, "d": "2026-08-14" }
]
```

`id` é opaco e vive só durante a chamada — não é o uuid da transação. O backend guarda o
mapa `id → uuid` em memória e recasa a resposta.

### 6.2 O schema da resposta

```ts
{
  responseMimeType: 'application/json',
  responseSchema: {
    type: 'array',
    items: {
      type: 'object',
      properties: {
        id:         { type: 'string' },
        category:   { type: 'string', enum: [/* as 10 */] },
        confidence: { type: 'number' }
      },
      required: ['id', 'category', 'confidence']
    }
  }
}
```

`responseSchema` reduz o risco de JSON quebrado — não elimina. A resposta passa por Zod
no servidor. Item com `id` desconhecido é descartado; transação sem resposta vira
`outros` com `confidence: 0` e `category_source: 'ai'`.

### 6.3 Custo e limites

- Lotes de **50 transações** por chamada.
- Teto de **20 lotes por import** (1.000 transações). Acima disso, o import é recusado
  com mensagem clara em vez de queimar cota em silêncio.
- Transação que casa com `rule` **não entra no lote**. Um mês já corrigido custa zero.

### 6.4 Insights

Gerados sob demanda por mês, uma chamada, gravados em `insights` e reexibidos do banco.
Botão "regerar" explícito. A entrada é o **agregado** (total por categoria no mês e no
mês anterior), nunca a lista de transações — insight não precisa ver linha a linha.

```ts
type InsightBody = {
  headline: string
  items: { text: string; severity: 'info' | 'atencao'; category: Categoria | null }[]
}
```

## 7. Privacidade — o que nunca sai da máquina

### 7.1 Regras de anonimização

Aplicadas em `description_clean` no servidor, antes de qualquer chamada:

| Alvo | Tratamento |
|---|---|
| CPF `\d{3}\.?\d{3}\.?\d{3}-?\d{2}` | removido |
| CNPJ `\d{2}\.?\d{3}\.?\d{3}/?\d{4}-?\d{2}` | removido |
| Agência/conta `AG\s*\d{4}`, `C/?C\s*[\d-]+` | removido |
| Sequência de 6+ dígitos | removida |
| E-mail, telefone, chave PIX aleatória (uuid) | removidos |
| Contraparte após `PIX ENVIADO`/`PIX RECEBIDO`/`TED`/`DOC`/`TRANSFERENCIA` | truncado — fica só a operação |

Nome de estabelecimento **permanece**, porque é exatamente o que permite categorizar.

### 7.2 O risco residual, dito em voz alta

Nome de estabelecimento pode revelar coisa sensível — uma clínica, uma farmácia, um
advogado. A v1 não resolve isso e **não vai fingir que resolve**. Fica registrado no
README como limitação conhecida, com a saída disponível ao usuário: marcar uma transação
como "não enviar à IA", que a deixa em `outros` sem nunca sair do servidor.

### 7.3 O teste que transforma promessa em asserção

```ts
// tests/anonymize.test.ts
it('nenhum payload de saída contém identificador', () => {
  for (const linha of fixtures) {
    const out = anonymize(linha)
    expect(out).not.toMatch(/\d{3}\.?\d{3}\.?\d{3}-?\d{2}/)          // CPF
    expect(out).not.toMatch(/\d{2}\.?\d{3}\.?\d{3}\/?\d{4}-?\d{2}/)  // CNPJ
    expect(out).not.toMatch(/\d{6,}/)
    for (const t of IDENTIDADE_DO_DONO) expect(out).not.toContain(t)
  }
})
```

O teste roda sobre fixtures derivadas de extrato real (§10). Sem ele, "o app anonimiza"
é uma frase no README.

### 7.4 LGPD

- **Exclusão de conta** em `/conta`: confirmação por digitação, `delete` do usuário no
  Supabase Auth, cascade real apagando as cinco tabelas. Zero linha órfã.
- **Retenção de arquivo:** nenhuma. O arquivo enviado não é persistido.
- **Base legal e transferência internacional:** a descrição anonimizada vai para o Google.
  Dito no README e na tela de import — não escondido.

## 9. Métricas de qualidade

Medidas a partir de E4, num extrato real de 1 mês:

| Métrica | Meta |
|---|---|
| Transações fora de `outros` | ≥ 80% |
| Categorias corrigidas manualmente | ≤ 15% |
| Chamadas ao Gemini no 2º mês (com regras já criadas) | ≤ 60% do 1º mês |
| Duplicatas em reimport | 0 |

A taxa de `outros` é o termômetro do prompt. Se subir, o problema é o prompt, não o banco.

## 10. Dados de desenvolvimento e conta demo

**São duas coisas diferentes e não se misturam.**

### Desenvolvimento — extrato real
Extratos reais do usuário, em `tests/fixtures/`, **fora do git** (`.gitignore`). São a
única forma de descobrir que cada banco escreve a mesma coisa de um jeito
(`Pagamento de fatura` × `PAGTO FATURA`). As fixtures versionadas são derivadas destas,
já anonimizadas.

### Conta demo — seed derivado, nunca o extrato cru
A conta demo fica atrás de um link público. O seed é **gerado a partir** do extrato real
por um script `scripts/seed-demo.ts`:

- descrições de estabelecimento mantidas (é o que dá realismo)
- toda linha passa pelo `anonymize` de §7.1 antes de entrar
- datas deslocadas por um offset fixo
- valores multiplicados por um fator (ex.: 0,83) e re-arredondados

Resultado: um extrato que **parece real porque é real na forma**, sem ser o do usuário.

> Isto é uma decisão de segurança, não de conveniência: o que entra num link público não
> volta atrás. Se a preferência mudar para usar o extrato cru no demo, é este parágrafo
> que muda — e a consequência precisa estar clara.

## 11. Riscos

| Risco | Mitigação |
|---|---|
| Banco exporta OFX fora do padrão | `OfxAdapter` tolerante + fallback para CSV com mapeamento |
| Gemini devolve JSON fora do schema | Zod no servidor; item inválido vira `outros`, nunca quebra o import |
| Free tier do Gemini acaba no meio do desenvolvimento | `LLMProvider` é interface; trocar provedor é uma classe nova |
| Prompt categoriza mal PIX e transferência | Previsto: são os campos mais pobres. As `rules` do usuário são a saída |
| Extrato grande estoura o timeout da Route Handler na Vercel | Teto de 1.000 transações por import; acima disso, recusa explícita |
| Reimport duplicando | `fingerprint` como id do documento + teste de aceite em E2 |
| Rollup mensal fora de sincronia com as transações | `recalcularRollup()` + teste que compara rollup com recálculo (§4.5) |
| Admin SDK ignora as Security Rules | Dados em subcoleção sob `users/{uid}`; sem uid não há caminho (§3.1) |
